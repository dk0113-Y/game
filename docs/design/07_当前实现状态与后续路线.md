# 当前实现状态与后续路线

## 已确定设计

当前已实现内容：

- Vite + React + TypeScript。
- `game/core` 与 UI 分层。
- 六边形坐标工具。
- 六边形视觉地图。
- settler 移动。
- 一格定居/扎营雏形。
- 地形潜力数据。
- `endTurn` 基础产出。
- Vitest 测试。

需要注意：当前代码命名仍以 `Settlement` / `foundSettlement` 为主。“扎营”和 `Camp` / `Site` 是设计语义和后续重命名方向，不是当前已完成实现。

当前未实现内容：

- 完整 AP 行动系统。
- Camp / Site 重命名。
- Improvement 开发设施。
- 技术图谱。
- 生产力指数。
- 时代切换。
- 统治集团 / 人物 / 家族。
- 政权压力测试。
- 程序化地图。
- 存档系统。
- AI。

## 暂定设计

推荐后续开发顺序：

1. 行动点 AP 与扎营语义修正。
2. Camp / Site 与 Improvement 最小闭环。
3. 小型测试地图。
4. 技术图谱第一版。
5. 生产力指数与第一次生产力革命。
6. 时代切换与 Legacy 折叠。
7. 统治集团与政权压力。
8. 程序化地图。
9. UI / 交互优化。
10. 存档与长期模拟。

短期内明确不建议做的内容：

- 完整科技树。
- 完整地图编辑器。
- 复杂 AI。
- 完整家族系统。
- 大规模世界地图。
- 过早接入 Steam / Electron。

## 后续实现建议

- 每个阶段都应有一个可运行、可测试的最小闭环。
- 新增核心规则时优先写在 `game/core` 或 `game/data`，UI 只负责交互和展示。
- Improvement 第一版可以只支持少数设施，例如农地、伐木营、采石场、观察点。
- 技术图谱第一版只需要验证隐藏、暴露、掌握三个状态。
- 生产力革命第一版只需要一次阶段切换，不要一开始覆盖全部时代。
- 政权压力系统第一版可先抽象为数值和事件，不必立即做人名、谱系和完整继承。

## 风险记录

- 如果过早做大地图和 AI，会掩盖早期规则还未闭环的问题。
- 如果把技术做成固定科技树，会削弱“环境契机驱动”的项目核心。
- 如果文明进步只提供正收益，会丢失“生产力革命冲击统治集团”的关键设计。
- 如果继续把早期行为称为建城，容易把玩家预期带向传统 4X 城市经营。

## 未决问题

- 下一步是否先做 AP 系统，还是先做 Camp / Site 数据重命名？
- Improvement 是否已经需要进入 `Tile` 状态，还是先放在单独索引表中？
- 第一版技术图谱应先验证哪条线：农业、马匹、水运、冶金还是交通？
- 生产力指数是否应在 UI 中早期可见？
